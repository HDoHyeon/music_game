# CLAUDE.md

## 1. 프로젝트 개요

- 프로젝트명: music_game
- 장르: 리듬게임 (DJMAX, EZ2ON 참고)
- 타겟 플랫폼: PC
- 프로젝트 개요 및 개발 환경은 `README.md`를 참조한다. (단, README.md를 참조할 때는 사용자의 허락을 먼저 구한다.)
- 이 문서는 Claude가 프로젝트에서 작업할 때 준수해야 할 규칙을 정의한다.

## 2. 개발 환경

- Unity: Unity 6.6 (6000.6.9f1, 실제 버전은 ProjectSettings/ProjectVersion.txt 확인)
- Render Pipeline: URP
- Scripting Backend: Mono
- Input System: Input System Package (New)
- 언어: C#
- 주요 에셋 및 추가 패키지: None (기존 설치 상태는 Packages/manifest.json 확인)
- 사용자 승인 없이 개발 환경, 패키지 또는 프로젝트 설정을 변경하지 않는다.

## 3. 핵심 작업 규칙

- 사용자가 요청한 작업 범위만 수행한다.
- 요청하지 않은 기능, UI, 시스템, 에셋을 임의로 추가하지 않는다.
- 추가 작업이 필요하다고 판단하면 이유와 영향을 설명하고 사용자에게 먼저 확인한다.
- 요구사항이 불명확하거나 여러 구현 방향이 가능하면 임의로 결정하지 않고 질문한다.
- 확인하지 않은 코드, 파일 경로, 클래스, 메서드가 존재한다고 가정하지 않는다.
- 기존 기능과 사용자 작업 내용을 보존한다.
- 관련 없는 코드 수정, 리팩터링, 파일 이동 및 삭제를 수행하지 않는다.
- 분석이나 계획만 요청받은 경우 코드를 구현하지 않는다.

## 4. 작업 진행 절차

### 4.1 분석

1. `README.md`와 관련 계획서를 확인한다.
2. 실제 소스 파일 및 필요한 프로젝트 설정을 읽는다.
3. 기존 코드 구조, 데이터 흐름, 의존성 및 관련 기능을 파악한다.
4. 수정 대상과 영향 범위를 확인한다.
5. 불명확한 요구사항이나 추가 작업이 필요한 부분은 사용자에게 질문한다.

분석 단계에서는 구현 코드를 수정하지 않는다.

### 4.2 계획

1. 요청받은 특정 작업에 대한 상세 구현 계획서를 작성한다.
2. 실제 코드베이스를 기반으로 수정 대상, 구현 방법 및 검증 방법을 작성한다.
3. 필요한 경우 계획서에 코드 스니펫을 포함한다.
4. 사용자가 요청한 범위를 벗어나는 기능은 계획에 포함하지 않는다.
5. 작성한 계획을 사용자에게 제시한다.

계획 단계에서는 실제 소스 코드를 수정하지 않는다.

### 4.3 사용자 검토 및 승인

- 사용자가 계획을 검토하고 구현을 승인할 때까지 기다린다.
- 수정 요청이 있으면 계획서를 먼저 수정한다.
- 계획 승인 없이 구현을 시작하지 않는다.

### 4.4 구현

- 승인된 계획서의 범위 내에서 작업한다.
- 기존 코드 구조와 스타일을 우선적으로 따른다.
- 계획과 다른 구현이 필요하면 변경 이유를 설명하고 사용자에게 확인한다.
- 구현 중 추가 기능이 필요해도 승인 없이 작업 범위를 확장하지 않는다.
- 완료한 작업과 남은 작업을 계획서에 기록한다.

### 4.5 검증

- 변경한 코드의 컴파일 오류 여부를 확인한다.
- 요청한 기능이 요구사항대로 동작하는지 검증한다.
- 변경으로 영향을 받는 기존 기능의 회귀 여부를 확인한다.
- Unity 실행이나 실제 플레이 테스트가 불가능하면 미검증 상태와 이유를 명시한다.
- 실행하지 않은 테스트를 통과했다고 보고하지 않는다.
- 검증 결과 및 미해결 문제를 계획서에 기록한다.

## 5. 구현 계획서 관리

- 계획서는 프로젝트 전체가 아닌 특정 작업 단위로 작성한다.
- 각 작업의 구현 전 및 진행 중에 해당 계획서를 사용한다.
- 계획서는 `plans/` 폴더에서 기능별로 관리한다.
- 파일명은 `<기능명>_plan.md` 형식을 사용한다.
- 기존 계획서가 있다면 먼저 확인하고 중복 문서를 생성하지 않는다.
- 사용자가 계획서 목록만 요청하면 상세 계획서나 코드를 작성하지 않는다.
- 계획서의 내용과 실제 구현 상태를 일치시킨다.

### 계획서 작성 형식

1. 작업 목적 및 요구사항
2. 기존 코드 분석
3. 작업 범위 및 수정 대상 파일
4. 상세 구현 방법 및 필요한 코드 스니펫
5. 구현 순서 및 진행 상태
6. 테스트 및 검증 방법
7. 검증 결과 및 미해결 사항

### 계획서 목록 관리

- 전체 기능별 계획서 목록은 `PLAN.md`에서 관리한다.
- 특정 기능을 작업할 때는 `PLAN.md`에서 해당 계획서를 확인한다.
- 상세 구현 내용은 `plans/` 폴더의 기능별 계획서를 참조한다.
- 신규 기능 추가 시 사용자 승인 후 `PLAN.md`에 등록한다.
- 목록에 있다는 이유만으로 구현을 시작하지 않는다.

## 6. 코드 작성 규칙

- 기존 C# 코드의 명명 규칙, 파일 구조 및 구현 방식을 따른다.
- 프로젝트의 실제 Unity 버전과 설정에서 지원하는 API를 사용한다.
- 입력 관련 구현은 Input System 패키지를 기준으로 한다.
- 요청한 기능에 필요한 최소한의 변경만 수행한다.
- 기존 코드로 해결할 수 있다면 불필요한 클래스나 시스템을 추가하지 않는다.
- 코드의 의도와 동작이 불명확한 부분에는 필요한 설명을 작성한다.
- 기존 동작을 변경할 경우 영향 범위를 먼저 확인한다.
- 지속적으로 typecheck를 실행해서 새로운 문제를 만들지 마라.
- 작성한 코드에는 이 코드가 하는일을 주석으로 표시하라.

## 7. PLAN.md 관리 규칙

- PLAN.md를 수정하려고 하면 작성자에게 먼저 허락을 요구하고 내용을 알린다.
- PLAN.md의 내용이 부족하거나 수정할 내용이 있따면 작성자에게 보고후 허락을 요구하고 내용을 수정한다.
- 프로젝트 전체가 아닌 특정 기능 또는 작업 단위로 작성한다.
- 개발 진행에 따라 기존 계획서를 지속적으로 수정하고 보완한다.
- 실제 구현 과정에서 변경된 내용은 계획서에 반영한다.
- 추가 구현이 필요한 경우 사용자에게 먼저 확인한다.
- 사용자 승인 없이 기존 요구사항이나 작업 범위를 변경하지 않는다.
- 완료된 작업, 진행 중인 작업, 남은 작업을 구분하여 관리한다.
- 계획서의 내용과 실제 코드의 구현 상태를 일치시킨다.

## 8. 금지 사항

- 사용자 승인 없는 기능 추가 및 요구사항 변경
- 계획 승인 전 실제 코드 구현
- 사용자 승인 없는 패키지 설치, 삭제 또는 버전 변경
- 사용자 승인 없는 Unity 프로젝트 설정 변경
- 관련 없는 파일 수정, 삭제, 이동 또는 리팩터링
- 실제 소스 확인 없이 클래스명, 파일 경로, 구현 상태를 단정하는 행위
- 실행하지 않은 테스트나 확인하지 않은 결과를 완료로 보고하는 행위
- any나 unknown 타입을 사용하는 행위

- 수정하거나 생성한 파일
- 테스트 및 검증 결과
- 미해결 문제 및 사용자 확인이 필요한 사항

사용자가 요청하지 않은 후속 작업은 임의로 진행하지 않는다.
